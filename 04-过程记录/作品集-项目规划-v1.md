## 一、先对齐招聘方要什么

初级 AI 应用开发岗的 JD，高频关键词其实就 6 组：

| JD 关键词 | 招聘方真正想看什么 | 你现在的证据 |
|---|---|---|
| Python 基础 | 能读懂、能改、能写函数 | 01→09 脚本，228 行结构化代码 |
| 大模型 API | 调通、处理报错、控制成本 | 已接通火山方舟，踩过模型名/接入点/重试的坑 |
| 提示词工程 | 能稳定产出可用结果 | 商业海报提示词 + 5 套风格模板库 |
| 工程化 | 异常处理、配置分离、版本管理 | 环境变量、重试、Git、.gitignore |
| 完整项目 | 有目标-过程-结果-复盘 | 有，但还没有"成品形态" |
| 部署/展示 | 别人能跑起来、能看到 | 今天开始解决（GitHub） |

**结论**：你不缺"做过"，缺的是**把做过的东西包装成"项目"**。这正是接下来 3 个项目的任务。

## 三、三个项目（按顺序做，不要并行）

### 项目 A · 暖爪咖啡 AI 文案工具链（升级现有 09）
**一句话**：输入产品名，30 秒输出海报提示词 + 三组小红书文案 + 存档。

- 现状：能跑，但缺"给别人看"的形态
- 要补的 4 件事：
  1. README 写清楚：解决什么问题、怎么装、怎么跑、输出长什么样
  2. 一张运行截图 + 一份示例输出文件（放 `examples/`）
  3. 补 3 条异常处理：网络失败重试（已有）、Key 缺失提示（已有）、AI 返回空内容兜底
  4. 一次性跑 3 个产品的批处理演示，证明稳定
- 验收：陌生人拿到仓库，5 分钟内能跑出结果
- 时间：Day 27–28（约 4 小时）

### 项目 B · AI 文案生成与管理工具（路线里的"作品集项目 2"）
**一句话**：不只生成，还能**管理**——历史记录、多平台版本、风格库可配置。

- 相比 09 新增：
  1. 结果存 JSON（不是散落的 txt），可按产品/风格检索
  2. 一次生成多平台版本（小红书 / 朋友圈 / 电商详情页，长度和语气不同）
  3. 风格库外置成 `styles.json`，不改代码也能加风格
  4. 简单交互：命令行菜单（后续可升级 Tkinter 界面）
  5. 输入校验：空输入、超长输入、非法风格都有友好提示
- 验收：能演示"同一产品出 3 个平台版本 + 历史可查"
- 时间：第 2 月（Day 31–45），约 12 小时
- 这一步会覆盖 JD 关键词：JSON、文件管理、模块拆分、CLI

### 项目 C · 可评测的 AI 工作流
**一句话**：不只说"效果好"，而是**用数据证明有多好**。

- 内容：
  1. 固定 20 条测试用例（产品名 + 期望风格 + 判定标准）
  2. 对比 2–3 套提示词版本的输出，记录：可用率、平均耗时、token 成本
  3. 写测试记录表 + 结论（哪版最好、为什么）
  4. 复盘：失败案例长什么样、怎么改提示词
- 验收：能给面试官讲"我用 20 条用例证明了版本 B 比版本 A 好 30%"
- 时间：第 3 月（Day 61–75），约 10 小时
- 这一步直接对应"AI 工作流/评测"岗位要求，是**拉开差距的项目**

## 五、每个项目的"能讲什么"（面试话术模板）

> **项目 A**：我做了个文案工具，输入产品名就能出海报提示词。过程中遇到模型返回不稳定，我加了重试和空值兜底；还发现启动器写死旧脚本导致改了没效果，最后靠时间戳比对定位。
>
> **项目 B**：我把单次生成升级成管理系统，结果存 JSON、风格可配置、多平台版本一次出。设计时最难的是一次生成多平台，我拆成了"内容核心 + 平台适配层"。
>
> **项目 C**：我做了一套评测，20 条用例跑 3 个提示词版本，记录可用率和成本，最后选出版本 B。这让我能说清楚"为什么这样写提示词"，而不是凭感觉。
